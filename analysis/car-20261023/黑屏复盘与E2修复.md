# E1 实车黑屏复盘与 E2 修复

记录时间：2026-10-23。结论：已找到并离线复现 E1 与 A7 视频解析器之间的一处确定不兼容，E2 已修复。E2 的实际 USB 接收、硬件解码与车机显示仍需实车验收。

## 1. 输入与去重

- 三个原始诊断 ZIP 位于本任务日期目录，分别为 OpenSAICLink-E1-1792715022253.zip、OpenSAICLink-E1-1792715188200.zip、OpenSAICLink-E1-1792715807777.zip，CRC 检查通过。
- 导出包含累计历史；按同名会话和录屏去重后为 10 份会话日志、4 段视频，不能把每个 ZIP 内的同一会话重复计为新的测试。
- 4 段中 1 段是此前 K80 本机自检，3 段来自实车测试。原始 ZIP、11 张工程模式照片、E1 APK 保留原位。
- 输入哈希见 [input-manifest.json](input-manifest.json)，去重及会话指标见 [car-results.json](car-results.json)。报告不复述日志中的手机/车机序列号和地址。

## 2. 已经通过和仍然失败的环节

车机先发送 onHuReady：Linux、1280×480、codecMode=3；E1 发送 onMuReady。收到 requestWeLink（linkMethod=3，车机 SDK V1.7.12012041）后，E1 回复 codecMode=2、1280×480；之后车机发来 type 8 的 config 30、控制状态及心跳。

这说明至少以下三个会话完成了应用层配置，但不能把它当作画面已显示：

| 会话日志后缀 | 最后一次统计：编码单元 | 完成写出的视频单元 | 丢弃数 | 观测 |
|---|---:|---:|---:|---|
| 081630 | 819 | 2 | 816 | 写出数停滞，队列持续丢帧；具体阻塞位置 E1 未记录 |
| 082226 | 1263 | 1263 | 0 | 持续写出约 3.43 MB，用户仍报告黑屏 |
| 083622 | 292 | 292 | 0 | 持续写出约 0.63 MB，用户仍报告黑屏 |

计数来自日志最后一次周期统计，不是完整文件最终帧数。其他短会话存在只打开 USB 未收到 config，或 EIO 断开；反复重开应用不一定会让车机重新发完整握手。

电脑软件解码结果：3 段实车录屏分别读出 927、1361、423 帧，均为 1280×480，画面非全黑；另一本机自检读出 1213 帧、1280×720。详见 [capture-health.json](capture-health.json)。因此持续写出会话的黑屏，不能仅解释为手机没录到画面或整条 USB 一直不通。

## 3. 确定的不兼容：三个内容被合成了一个协议包

视频初始化需要两段解码参数 SPS、PPS，以及一幅完整的关键帧 IDR。E1 生成的 H.264 码流本身可以被电脑解码，但它把三者合进了一个 WL type 6 载荷。

A7 包内 SaicLink 的 `_mware_decoder_get_h264_info` 按载荷首先识别到的 NAL 分类。载荷以 SPS 开始时，函数将整个载荷缓存到 SPS 分支，然后返回；不会继续把同包里的 PPS 和 IDR 逐一处理。因此关键帧回调没有发生，后续非关键帧也无法替代这一步初始化。

当前匹配手机版本 base.apk 的 DEX 指令再次确认：`f$1.onOutputFormatChanged` 分别取出 csd-0 和 csd-1，并各调用一次 WLCodecListener.onCallBack；它们不是合并成一个回调。这与 A7 接收器要求一致。指令证据：

- [当前 APK 编码回调](current-com.wedrive.android.welink.a.f$1.dexasm.txt)
- [当前 APK 视频转发回调](current-com.wedrive.android.welink.a.c$1.dexasm.txt)
- [A7 原函数反汇编](hu-h264-parser-disassembly.txt)

## 4. 怎样在没有手机和车的情况下复现

从已下载的 A7 app-pkg.bin 中只读提取 SaicLink，使用 Unicorn 2.1.4 重放原 ARM Thumb 解析指令。绑定 ELF SHA-256：

`835f2d3a6485c52111c5360c34ef665bcf2b1a26969cd7cea8747fc8f2275ced`

入口为 0x73241。内存分配、日志、图像回调等外部调用使用测试桩；每次执行设指令和时间上限。未启动完整固件，也未模拟 USB、硬件解码器或液晶显示。

从三段真实 K80 实车录屏分别取出首个访问单元，用 E1 单包方式与 E2 实际 Java 分包器输出驱动同一解析函数：

| 录屏后缀 | E1 首包字节数 | E1 图像回调 | E2 载荷长度（SPS / PPS / IDR） | E2 关键帧回调 | 接收器重组字节 |
|---|---:|---:|---|---:|---|
| 4781165 | 22125 | 0 | 21 / 8 / 22096 | 1 | 与原单元完全相同 |
| 4968599 | 22542 | 0 | 21 / 8 / 22513 | 1 | 与原单元完全相同 |
| 5789931 | 23080 | 0 | 21 / 8 / 23051 | 1 | 与原单元完全相同 |

详见 [hu-parser-replay.json](hu-parser-replay.json)。这是可复现的软件协议不兼容与修复证据；它尚不能证明整车硬件链路已经恢复。

## 5. E2 修改

- SPS、PPS 独立发送，每幅图像的多个 slice 保留在同一访问单元，避免把多片图像错误地拆成多帧。
- 采用与原版相同的 8 字节协议头和完整载荷分别写入方式，取消 E1 的 16 KiB 载荷分段写入。此项对齐发送行为，不能据此宣称第一次会话的 USB 停滞已解决。
- 日志分别记录完整视频单元、实际 WL 视频包数量，首批包记录 NAL 类型和写入耗时；写入超过 3 秒时记录 USB_TX_STALLED 和头/载荷所在阶段。
- 保留已收到 config 的握手参数、H.264 Baseline Level 3.1 和前台录屏流程。触摸回传与 USB 音频仍未实现。
